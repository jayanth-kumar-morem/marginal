# TEE security fact-check for SPEC.md (Marginal)

Compiled 2026-11-11. Scope: MOONSHOT.md §2 "What is genuinely hard", §3.1 rows 1 and 6, §3.2 items 2 and 7, §4.4 items 7–8, §4.5–4.6, §12 technical rows; moonshot-notes/papers.md sections A and B, the RAND row in H, and "Hard technical facts" (HTF) 3, 4 and 9.

**Method.**
- Researchers' own sites and vendor docs were fetched with WebFetch.
- arXiv metadata and abstracts were pulled verbatim from the export API (`https://export.arxiv.org/api/query?id_list=...`) on 2026-11-11.
- Where a number was not in an abstract, the arXiv HTML full text was grepped for the exact sentence.
- "Search summary" means the fact came from a search-engine result summary, and the page itself was not fetched or could not be fetched. Treat those as weaker than fetched text.

**Source types.** PRIMARY = vendor docs or advisories, the paper itself, the researchers' own site. SECONDARY = press, aggregators, third-party blogs. UNVERIFIED = could not confirm.

### E. Design implications (my analysis, derived from the sources above)

- **D1. Key the value cap to the physical platform, not the room key.** Use the Intel PPID/PCK certificate or the AMD chip identity. One extracted PCK (TEE.fail) or one compromised host (DDRop) can mint any number of valid-looking room keys. Basis: V1, V10, N21.
- **D2. Cross-vendor re-execution raises integrity but lowers confidentiality.** Every re-executing room sees the plaintext, so exposure becomes the union of the vendors' weaknesses, unlike SVR3's secret sharing. Re-execute only on challenge, on as few rooms as possible, and consider re-running only the deterministic scorers. Basis: N23, V26.
- **D3. Count diversity as CPU-TEE vendor × operator × facility.** NVIDIA GPU CC is a shared dependency, not a vendor (N9). Nitro's parent instance is the operator (N4).
- **D4. Make the attestation policy a versioned, on-chain object.** It should include: a minimum TDX module version (N3); SEV-SNP firmware with the BadRAM fix (V34); StackWarp microcode and SMT off (N2); a freshness SLA for CRLs and TCB info (N5); a PPID or chip allow-list (N21, N28); and an automatic admission freeze on public disclosure (N27).
- **D5. Set T1 caps from the cost of physical access, not hardware.** Hardware costs $10–$1k; the binding cost is physical access to an allow-listed host, so size caps from the cost of corrupting an insider at an allow-listed facility, plus insurance.
- **D6. SPEC wording fixes:**
  - Do not claim HBM encryption on either GPU generation.
  - Say Blackwell is "TEE-I/O capable", not "TEE-I/O protected".
  - Describe TOPLOC as "significantly faster" (current version), with no 100×.
  - Say TEE.fail *relays* NVIDIA attestation; it does not forge it.
  - State 2505.16501 as "non-CC throughput 45–70% higher".
  - State 2602.11088 as "~6 min per layer".
  - Cite 2608.26575, not 2409.03992, for a 100B+ appraiser.
  - Attribute the 95–99% figure to PromptPeek.
  - Cite OTR only for "TEE + fraud-proof fallback".
- **D7. Room liveness is not guaranteed.** NVIDIA says CC does not guarantee availability (N10), and NRAS outages block ITA tokens (N16). Keep yield/resume timeouts and refunds as hard requirements.
- **D8. The dstack KMS fallback concentrates key risk.** Prefer NEAR MPC CKD (threshold), and treat dstack KMS as a time-limited fallback with low caps (N22, N27).
- **D9. Prefer whole-node allocation for multi-GPU rooms.** NVBleed shows NVLink leakage across VMs outside CC (N7), and 2507.02770 shows plaintext RPC metadata that can be reordered (V19). Pad and batch, as MOONSHOT already says, and do not share NVLink fabrics with other tenants.
